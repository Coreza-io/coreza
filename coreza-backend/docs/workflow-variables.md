# Read-only workflow configuration variables

`{{ $vars.BASE_RISK }}` returns a typed scalar; arithmetic and quoted keys use the existing safe parser. `$vars` is separate from mutable Store data and `$state`. It is user-owned configuration, never a credential store. Names follow `[A-Za-z_][A-Za-z0-9_]*`; prototype keys are rejected. Limits: 128 variables, 64 ASCII characters per name, 4 KB per serialized scalar and 64 KB per snapshot. Arrays and objects are excluded in v1.

## Consistency and lifecycle

PostgreSQL is authoritative. All mutations lock one user revision row, check the caller's expected revision and increment the revision in the same transaction, including deletion. Direct table writes are revoked; RLS isolates authenticated reads and RPCs verify the owner. Backend callers derive ownership from verified JWTs or the existing owned-workflow lifecycle. Revision strings avoid JavaScript integer precision loss. No global/project hierarchy is introduced.

Before an execution using `$vars` starts, verify PostgreSQL's current revision. Read the immutable Redis payload at `coreza:vars:v1:<hashed-user>:<revision>` using the existing **cache** client. On miss, malformed/oversized entry, timeout or Redis outage, load one consistent SQL snapshot and optionally fill that revision's key. Redis uses a 500 ms optional-operation timeout. Payload TTL defaults to 300 seconds with jitter and is configurable between 30 and 3600 seconds; TTL controls resource use, not correctness. SQL revision verification is mandatory, even on a cache hit: database unavailability prevents startup. This intentionally trades one lightweight SQL revision call at startup for fail-closed consistency.

Concurrent payload misses coalesce per owner/revision with a maximum of 128 pending loads. Mutation deletes the previous revision key after commit; failed invalidation is harmless to correctness because new startups verify the DB revision and cannot select the old key. An earlier in-flight load can populate only its immutable revision key. No Pub/Sub freshness guarantee or mutable process-global variable registry exists.

Live runners initialize before consumer-group processing, pending-message reclamation or acknowledgment. A frozen runner-local snapshot survives `resetForNextBar(true)`. Stop/failure releases both the snapshot and expression-context reference. Restart/recovery loads a fresh revision. Live run records retain only `variable_revision`, through Redis and PostgreSQL run synchronization. Values are never added to the workflow graph, node context outputs or run metadata; expression results can naturally be used as node parameters/outputs.

Short server runs and backtest sessions use the same `WorkflowRun.initialize` boundary. Generic `$vars` expressions and variable-dependent typed Edit Fields take the bounded runtime resolver rather than the legacy compiled-slot shortcut. Typed Edit Fields inject the same read-only root while preserving `$state`, node identities, budgets and transport semantics. Expressions do no asynchronous I/O.

Editor manual/cluster actions pin one snapshot per execution-lock token, scoped to the authenticated user. They send only its revision and ordinary resolved parameters. Typed Edit Fields retain expressions and obtain authoritative variables on the server. If variables change between actions, a revision mismatch aborts further actions with 409 instead of mixing configurations; restart the editor execution. Preview uses a separate current snapshot and does not promise to show an already-running live runner's pinned revision. Settings mutation invalidates the owner's preview query; variable-name suggestions are available in generic expression inputs. Snapshot values are not logged by the variable service, and variable-dependent editor request payload logging is suppressed. Backend node/request logs omit raw resolved payloads, search queries, agent prompts and tool inputs. Manual snapshot middleware loads only for an explicit revision or typed Edit Fields expression; Fixed literals and unrelated request data never trigger a load.

## Rollout

1. Apply `supabase/migrations/20261012080000_workflow_variables.sql` before deploying reads. The migration is idempotent; it adds revisioned RPCs, read policies, scalar constraints and nullable live-run revision metadata. RPC adapters follow the repository's existing narrow RPC typing pattern; no generated client types are edited manually.
2. Deploy backend with `WORKFLOW_VARIABLES_ENABLED=false` (default). Optional `WORKFLOW_VARIABLE_CACHE_TTL_SECONDS` controls cache retention. Use the existing Redis cache connection; no queue connection or new runtime is introduced.
3. Run disposable PostgreSQL integration tests and existing execution regressions. Enable `WORKFLOW_VARIABLES_ENABLED=true` only after these deployment gates pass.
4. Build frontend with `VITE_WORKFLOW_VARIABLES_ENABLED=true` only after backend support is enabled. This adds Settings → Variables, authenticated CRUD, previews and input suggestions. The frontend flag defaults off. Fixed fields and workflows without variable references retain existing execution paths.
5. Observe bounded metrics: `coreza_variable_snapshot_loads_total`, `coreza_variable_snapshot_load_seconds`, snapshot size/count histograms and active pinned snapshots. No user IDs, keys or values are metric labels. Measure cache hit/miss and startup latency in the deployed topology before tuning TTL. Alert on load failures and repeated SQL fallbacks.

Configuration edits affect **new runs only**; restart active live strategies to apply them. Hot reload is not implemented. Rollback disables frontend authoring and prevents *new* variable-dependent runs by disabling the backend flag; already-started live runners keep their pinned configuration until stopped. Stored variables remain in PostgreSQL. Do not silently execute variable-dependent expressions with an empty registry.

## Validation

Run `jest --runInBand tests/workflowVariables.test.ts tests/workflowVariableLifecycle.test.ts tests/variableContext.test.ts tests/safeExpression.test.ts tests/editFieldsV2.test.ts`. New coverage includes owner-isolated cache payloads, immutable scalar values, stale revisions, invalid keys/types, SQL fallback, fail-closed startup, mode preservation, Fixed request literals, revision middleware failures, payload-free utility logging, compiled backtest fallback, typed/generic parity, cancellation/release, 10,000 expression reads without I/O and 10,000 full bar resets without reload.

PostgreSQL integration tests are opt-in with `VARIABLES_TEST_DATABASE_URL`: an **empty disposable database** whose name ends `_variables_test`, with permission to create test roles. Run `jest --runInBand tests/integration/workflowVariables.test.ts`. The suite bootstraps minimal Supabase auth helpers, applies the migration twice, verifies transactional revision conflicts/deletion/type round-trips and authenticated RLS/RPC isolation, and rolls everything back. Never point this at application data.

`node --import tsx scripts/benchmark-variables.ts` reports P50/P95 for 10,000 in-memory evaluations and bounded fixture size/heap change. This is a reproducible local evaluator benchmark, not a production startup/Redis/SQL latency claim. Deployments must measure those paths and representative strategy processing before enabling authoring. Recording/replaying historical variable revisions and live hot reload remain future work.
