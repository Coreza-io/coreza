# Scope workflow variables to the editor session or execution

## Cause on dev

The Variables tab reads [`useVariableSnapshot.ts`](../../src/hooks/useVariableSnapshot.ts), keyed by user and workflow ID, via [`GET /variables/snapshot`](../../coreza-backend/src/routes/variables.ts). The [snapshot service](../../coreza-backend/src/variables/VariableSnapshotService.ts) checks a database revision and loads saved workflow rows on a cache miss. Redis expires only its cached copy. That explains how an old workflow can still show `$vars.bonus = 2`, `$vars.long_entry = false` and `$vars.long_fail = false` after reopening.

Manual typed Edit Fields writes those rows in [`routes/comparator.ts`](../../coreza-backend/src/routes/comparator.ts) through the SQL-backed service. The editor action lock currently drops only the client invocation snapshot. The visible **Execute All** button also uses ordinary node actions through [`WorkflowEditor.tsx`](../../src/pages/WorkflowEditor.tsx) and [`WorkflowExecutor.executeAllNodes`](../../src/utils/workflowExecutor.ts). Changing only the backend workflow engine would miss this button. [`WorkflowRun`](../../coreza-backend/src/engine/workflowRun.ts) also loads the old workflow snapshot for server runs. Backtest writes already use a local overlay, but the starting values still come from that snapshot. Standard live writes go to SQL. When live write-behind is enabled for an eligible scope, the current stop [handoff](../../supabase/migrations/20261013100000_live_variable_checkpoints.sql) copies final values back to workflow rows.

## Target behavior

| Entry point | Scope and initial values | End of scope |
| --- | --- | --- |
| Manual editor actions, including a single node with upstream execution and Cluster Execute | Current `workflowSessionId`. Starts empty. Later actions in that same open editor can use values created by a prior action. | Clear on editor disposal, workflow or account change, import, or reload. Another tab has its own session. |
| Editor **Execute All** | One new ID per accepted Execute All invocation. Starts empty even if manual values exist. A variable appears only after an eligible Edit Fields node actually runs and commits it. Keep values across loop iterations and editor backtest bars inside the batch. | Drop on success, failure, or Stop. Restore the view of the separate manual session when the batch ends. |
| Server Run All or server backtest | One empty registry per `WorkflowRun` or server backtest session. Keep it across bars and loops within that run. | Release through existing run or backtest teardown on completion, failure, cancellation, or session expiry. |
| Live | One empty in-memory registry per live runner instance. Keep it across events for that activation. A later activation starts empty. | Stop admitting work, settle the in-flight event through the existing stop path, and release the registry on teardown. Treat loss of a variable-dependent worker as an interruption of that activation. A fresh activation initializes its own values. |

Keep `$vars` syntax and typed Edit Fields **Persistent** as the write switch. Update its helper text to describe the scope. Missing keys retain the current expression diagnostic. A strategy that depends on a starting value must execute its initializer before the first reader, including its first live event or backtest warm-up if applicable. Keep existing scalar and size limits, whole-batch validation, overwrite behavior, sequential Loop behavior, and the distributed Parallel Loop restriction. Scope values stay outside graph serialization, history, node results and pins. Store, `$state`, and legacy Edit rows keep their own behavior.

## Implementation

### 1. Give editor node actions an explicit scope

- In [`editorNodeExecution.ts`](../../src/services/editorNodeExecution.ts), bind the variable scope to the existing action lock when it is acquired. Single-node and cluster locks select the editor session. `executeAcceptedRun` selects a fresh batch UUID for the no-`nodeId` Execute All branch once preparation accepts the current session. The single-node branch still selects the editor session. Pass the same batch scope to every action, including repeated bars and Loop feedback paths. Keep the existing lock and generation guards.
- In [`useNodeExecution.ts`](../../src/hooks/useNodeExecution.ts), include the selected scope identity with `variableRevision` when loading or using `$vars`. Keep the existing guarded publication and strip `variableSnapshot` from node output as today. Key the local snapshot/query by owner, workflow, editor session and batch ID where applicable. The server backtest and live engine own their runtime registries separately from browser actions.
- In [`useVariableSnapshot.ts`](../../src/hooks/useVariableSnapshot.ts), [`InputPanel.tsx`](../../src/utils/InputPanel.tsx), and [`useNodeReferences.ts`](../../src/hooks/useNodeReferences.ts), use the same explicit scope for the Variables list, suggestions and expression preview. Thread the existing session ID through their node callers. Preview is read-only and shows an empty state for a scope with no committed entries. During Execute All, preview follows that batch and drops it at completion. The editor does not subscribe to live runner RAM. Keep the current saved-workflow requirement and ownership checks.

### 2. Keep editor request state in shared Redis

- Use the existing shared backend Redis connection and key helpers for one bounded record per `owner + workflow + editor session + mode + batch ID if present`. Extend [`routes/variables.ts`](../../coreza-backend/src/routes/variables.ts) with scoped lifecycle operations. Authenticate using the server-derived owner, verify workflow access, and validate scope mode and IDs. Open a scope only on first variable-related execution. A newly opened scope has a revision and zero entries. Preview can read an empty snapshot before open without allocating or extending the scope.
- Switch [`variableContext.ts`](../../coreza-backend/src/middleware/variableContext.ts) and the typed Persistent route to the scoped snapshot. Keep evaluation server-side and stage the whole batch before publishing. Reuse the current contract and overlay helper. Apply the update with an atomic Redis revision check, and use the existing invocation UUID for bounded, scope-local retry handling. A competing revision fails as a conflict. A retry after close or expiry cannot recreate values. Client-supplied scope IDs identify the record and never supply its authoritative values. If Redis is unavailable, variable-dependent editor actions fail clearly.
- Use one idempotent close operation that atomically discards values and leaves only an expiring closed marker for delayed requests. Invoke it in Execute All's existing `finally` and editor-session teardown. Immediately clear the corresponding client state, and use the existing execution-current checks to reject late responses. Closing must work if a request is in flight, including close racing the first open. Scope IDs are single-use after close. An expired active scope returns an explicit expiration result on continued use, with no automatic reseeding mid-action.
- Use a 24-hour inactivity TTL as the fallback for a closed tab, abandoned session or missed close request. Refresh only on active execution, never on preview polling. Active Execute All must renew through its existing execution path, including a long-running step if it can exceed the idle TTL. Use the existing close hooks for normal cleanup and the TTL for missed cleanup.

### 3. Reuse the run-local overlay for server batch, backtest and live

- In [`workflowRun.ts`](../../coreza-backend/src/engine/workflowRun.ts), initialize an empty snapshot only for graphs that use `$vars` or contain a typed Persistent Edit. Use the existing immutable overlay for commits in every runtime mode. The registry may be initialized empty before execution. Entries are created only by successful node commits. Keep the same registry across `resetForNextBar` and live event resets.
- Keep release tied to `WorkflowRun.destroy()`. Route terminal handling through the existing [one-shot engine wrapper](../../coreza-backend/src/engine/workflowEngine.ts), [worker and pooled run paths](../../coreza-backend/src/utils/workflowWorker.ts), [server backtest teardown](../../coreza-backend/src/backtest/session/BacktestSession.ts), and [live runner stop](../../coreza-backend/src/services/WorkflowRunner.ts) plus its manager's failure handling. On live stop, wait for the active event to settle before releasing the scope. An incomplete stop stays incomplete and must not admit a replacement as if teardown had succeeded. Avoid per-tick Redis or SQL work for variables.
- End new admissions to the old live variable write-behind path when this lifecycle policy goes live. Existing owned scopes must finish the current fenced stop/handoff before rollout. If an owned scope needs recovery, keep the existing recovery handling and block replacement until ownership is resolved. Retain the checkpoint code and worker for that transition. New ephemeral activations never read, checkpoint or hand off legacy variable values. Worker restart cannot resume an interrupted variable-dependent activation as though it still has its old variable state.

### 4. Cut over reads and writes together

- Remove legacy SQL snapshot and commit calls from normal editor and runtime entry points. Keep the explicit legacy-global export separate. Leave existing workflow rows, cache entries, receipts and checkpoint records out of the active namespace. The stale values disappear from the panel and runtime once both use scoped state. No database purge, schema migration, or automatic copy of old values is needed for this fix.
- Update the [architecture rule](../../AGENTS.md) and [variable documentation](../../coreza-backend/docs/workflow-variables.md) with the new lifetime contract. Deploy scoped backend and matching editor together. Once the policy switches, stale clients without scope metadata receive a refresh-required error for variable actions. They must not fall through to workflow SQL writes.
- Bound the change to typed `$vars` lifecycle and its editor display. Preserve unrelated node outputs, execution history, scheduling, and live order handling. This is a plan-only change. No implementation or testing is included.
