# Supabase setup alignment and cash snapshot retirement

5 November 2026 · Implementation plan for `dev`

## Current state

- The setup wizard in `setup/setup.js` deletes timestamped SQL files in the checkout, copies `setup/database-schema.sql` to `00000000000000_coreza_initial_schema.sql`, and runs `supabase db push`. On a history mismatch it can take a version from CLI output and mark it reverted. That changes migration bookkeeping without undoing the corresponding SQL, and can cause a later push to replay DDL.
- The bootstrap SQL already contains the shared reporting migration, including `live_strategies`, `portfolio`, and `trades`. It omits the portfolio equity OHLC columns and constraint from `20261028083211_portfolio_equity_ohlc.sql`, `users.selected_markets` and its constraint from `20261030064352_selected_markets.sql`, and the hierarchy writer guard and readiness RPC from `20261009090000_cluster_hierarchy_writer_guard.sql`. `setup/validate.js` requires the literal `CREATE TABLE IF NOT EXISTS`, so it reports valid reporting tables declared with plain `CREATE TABLE` as missing.
- The connected Coreza Supabase project has the reporting tables, the equity OHLC columns, `users.selected_markets`, the hierarchy guard and readiness functions, and Realtime publication membership for the reporting tables. Its migration list omits the October reporting/OHLC/market migration versions even though the corresponding objects exist. Treat the actual object definitions and the ledger as separate checks.
- On the reviewed `dev` revision, Live and Backtest read snapshots from `portfolio`. The live snapshot worker still calls `CashSnapshotRepository`: complete workflow/execution scope is routed to `portfolio` with the execution UUID as the strategy ID, while missing scope falls back to `cash_snapshots`. The connected project has **737 legacy cash snapshots**. All have workflow and execution IDs, but **zero** match a live reporting header by owner, workflow, and execution, and zero share a primary key with a row in `portfolio`. The catalog check found no incoming foreign keys, dependent views, Realtime membership, or references in public/private SQL function bodies. Deployed bundles, worker versions, external readers, and scheduled SQL still need an inventory before retirement.

## 1. Align fresh setup and existing upgrades

| Area | Implementation |
| --- | --- |
| `setup/setup.js` | Replace the destructive preparation and automatic history repair with explicit fresh and existing-project paths. Stage the selected migration set and Supabase config in an isolated work directory if the wizard needs to generate files. Verify the target project and migration state before writes. Surface a history mismatch with the versions and manual reconciliation steps. Continue to Edge Functions and secrets only after the schema step succeeds. |
| `setup/database-schema.sql` | Make the fresh-install schema match the reviewed `dev` runtime contract. Reuse the existing reporting DDL and fold in the OHLC and selected-markets changes exactly once. Port the canonical workflow document writer and hierarchy guard/readiness contract as a unit, including the current run columns, constraints, trigger, and RPC grants. Compare baseline against the ordered migrations for required extensions, RPC signatures, indexes, policies, grants, and publications. Preserve `backtests` and `live_fills`, and keep legacy data and retired SQL variable objects on existing projects outside this cleanup. |
| `setup/validate.js` and setup completion checks | Accept both forms of `CREATE TABLE` in static validation. Check the actual target contract after migration for the reporting tables, OHLC constraint, selected-markets constraint, hierarchy readiness, and Realtime membership. Validate least-privilege grants and owner RLS. A catalog or service-role check alone cannot confirm that an authenticated user can read their own rows. |
| `README.md` and database types | Document the fresh-install and upgrade commands where users already start setup, and replace the dead setup-guide link. Compare generated types from a verified schema with `src/integrations/supabase/types.ts`, `coreza-backend/src/types/supabase.ts`, and the shared reporting types in `coreza-backend/src/reporting/database.ts`. Update only the affected definitions and retain the legacy table type through the compatibility window. |

**Fresh Supabase project.** Apply the aligned bootstrap once on a verified empty Coreza schema, using its own versioned baseline. Include explicit grants for required Data API operations on fresh projects, including applicable sequence privileges, with existing ownership checks enforced by RLS. Keep reporting writes and privileged RPCs service-role only. Check config and credentials through the existing wizard inputs. Keep the baseline immutable after release and ship later schema changes as forward migrations. Do not stage the historical migrations on top of SQL already included in the baseline.

**Existing project.** Detect which install lineage the database uses before selecting migrations. For projects with the checked-in history, compare the versioned files and the remote ledger, and review a dry run before applying pending DDL. For projects with an older installer baseline, compare the actual schema to supported baselines and apply only the verified forward delta in that lineage. Do not overwrite an already-recorded bootstrap under the same version. For the connected Coreza project, compare actual definitions, grants, and any data steps before manually reconciling missing or differing ledger entries. Record a version as applied only after verifying its effects. Stop on unknown or partial schema state, and give the operator the discrepancy to resolve.

## 2. Retire the cash snapshot fallback before retiring the table

1. Verify snapshot producers and queued payloads in each deployed environment. Check the Portfolio executor, buffered snapshot producers, the fill sync worker, and scheduled/webhook activation identity. New strategy snapshots must carry the accepted reporting activation UUID along with owner and workflow. Manual and account-only activity should enter strategy reporting only if it has a valid reporting activation. If a genuine consumer still requires account-level history, keep `cash_snapshots` until that requirement has a supported destination.
2. After that check, make the snapshot worker's persistence path upsert valid live rows into `portfolio` only. Keep the stable snapshot UUID, database scope validation, dirty-metrics signaling, existing coalescing and atomic compare/delete after successful persistence. Route old or malformed entries with missing or unverified scope to bounded, observable handling for review. Preserve their payloads until explicitly resolved, avoid infinite retries for permanent scope errors, and keep transient write failures retryable. Keep database I/O in the existing worker, with no additional database query on the tick path.
3. Historical rows are intentionally discarded without archiving or reconciliation. Do not infer parents, create synthetic activations, or merge history into the latest run.
4. Deploy the matching workers, API and browser bundles while retaining the legacy table. Drain or classify old buffered snapshots and confirm that legacy reads and writes have ceased across all deployments, including older rollback versions, external consumers and scheduled SQL.
5. If all retirement conditions pass, use a separate forward migration with a restrictive drop, without `CASCADE`. Keep released baseline SQL and historical migrations immutable. On fresh projects, omit the table in the new baseline if it has yet to ship. If the released baseline already creates it, stage the retirement migration after that baseline so the completed installation has no legacy table or policy. Remove the table from the final schema inventory, application type, and stale documentation. Rollback versions must support the retired schema; historical data will not be retained.

## Release checks

- On a disposable fresh project, verify reporting tables and RPCs, the hierarchy readiness guard, observed backtest equity candles, selected-market defaults, and required Realtime events. Verify authenticated users see only their own reporting rows and that only the intended backend role writes reporting data.
- On a disposable copy of an existing install, verify upgrade and rerun behavior, migration history preservation, and that a failed preflight stops before schema writes and function deployment. Check both supported install lineages.
- Verify live and backtest results, a repeated snapshot write with the same ID, an invalid or legacy payload, and stop-time drain. Verify raw fill reads and writes still use `live_fills`. Before any table drop, confirm absence of active dependencies.
